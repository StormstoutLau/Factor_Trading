## 零、核心原则

1. **所有非 trivial 变更必须先有 Spec 文档，再有代码。**
2. **Spec 文档之间必须交叉验证一致性，消除幻觉和矛盾。**
3. **TDD 是代码实现的唯一入口——先写测试，再写实现。**
4. **每个阶段结束时必须 Review 通过才能进入下一阶段。**

---

## 一、Spec 开发流程总览

```
Phase 0: 调研 ──────────► 调研文档 (RESEARCH_xxx.md)
         │                     │
         │  Review: 排除幻觉    │
         ▼                     ▼
Phase 1: 设计 ──────────► 设计文档 (DESIGN_xxx.md)
         │                     │
         │  Review: 排除幻觉    │
         ▼                     ▼
Phase 2: 实施规划 ───────► 实施文档 (IMPL_xxx.md)
         │                     │
         │  Review: 排除幻觉    │
         ▼                     ▼
Phase 3: 验收标准 ───────► 审查清单 (CHECKLIST_xxx.md)
         │                     │
         │  Review: 文档一致性  │
         ▼                     ▼
Phase 4: TDD 实现 ───────► 测试 + 代码
         │                     │
         │  Review: 审查验收    │
         ▼                     ▼
Phase 5: 完成 ───────────► 归档 + 更新 DEVLOG.md
```

## 二、Phase 0: 调研 (Research)

### 目标
回答"我们要做什么？别人怎么做的？有什么坑？"——不涉及任何实现细节。

### 工具
- MCP 学术搜索: `search_papers`, `search_arxiv`, `search_semantic` 等
- MCP 网页搜索: `search_web`, `search_news`
- WebFetch: 获取论文全文、技术博客
- 本地代码库搜索: `SearchCodebase`, `Grep`

### 产出: `docs/RESEARCH_<topic>.md`

**必须包含的章节：**

```markdown
# [主题] · 调研文档

## 1. 问题定义
- 核心问题是什么？
- 为什么现在需要解决？
- 影响范围（哪些模块？）

## 2. 文献调研
- 学术论文（标题 + 链接 + 关键发现）
- 开源实现（仓库 + 成熟度评估）
- 工业界实践（框架/公司 + 做法）

## 3. 方案对比
- 方案 A: 描述 + 优点 + 缺点
- 方案 B: 描述 + 优点 + 缺点
- 方案 C: 描述 + 优点 + 缺点
- 非 trivial 决策：按 §11.8 的 7 维矩阵（成本 / 收益 / 兼容 / 维护 / 升级潜力 / 短期 / 长期）逐格取证
- 每方案 ≥2 个外部 T1/T2 锚点，覆盖 ≥3 个维度；无锚点标 `[无外部锚点-自证]`
- 选型决策 + 理由 + 被拒方案代价

## 4. 风险识别
- 已知风险 + 缓解策略
- 未知风险 + 如何探测

## 5. 调研结论
- 推荐方案
- 关键假设
- 下一步
```

### Review 检查点（Phase 0 → Phase 1 闸门）

| 检查项 | 通过标准 |
|--------|---------|
| 幻觉排除 | 所有论文/项目可验证（有链接/DOI），不存在虚构引用 |
| 方案完整性 | 至少对比 2 个方案；非 trivial 决策有 §11.8 的 7 维矩阵；每方案 ≥2 个外部 T1/T2 锚点覆盖 ≥3 维；选型有理由与被拒代价 |
| 风险覆盖 | 至少列出 3 个已知风险 + 缓解策略 |
| 假设明确 | 关键假设被显式声明，后续可验证 |

## 三、Phase 1: 设计 (Design)

> 搜索工具与外部案例锚点的硬约束见 §十一。

### 目标
回答"怎么做？架构是什么？接口长什么样？"——基于调研文档，产出可审查的设计。

### 产出: `docs/DESIGN_<topic>.md`

**必须包含的章节：**

```markdown
# [主题] · 设计文档

## 1. 设计目标
- 基于调研文档的选型决策
- 量化的设计目标（如"延迟 < 10ms"、"代码行数 < 500"）

## 2. 架构设计
- 模块分解图（ASCII art）
- 数据流图
- 模块职责边界

## 2A. 方案对比矩阵（Type-1 决策必填）
- 按 §11.8 的 7 维矩阵逐格取证
- 每方案 ≥2 个外部 T1/T2 锚点覆盖 ≥3 维；无锚点标 `[无外部锚点-自证]`
- 收敛出口：选定方案 + 理由 + 被拒代价 + 未决项四元块

## 3. 接口定义
- 公开 API 签名（函数名 + 参数类型 + 返回类型 + 异常）
- 配置项定义（字段名 + 类型 + 默认值 + 约束）
- 向后兼容性说明

## 4. 依赖分析
- 运行时依赖（包名 + 版本约束 + 用途）
- 内部依赖（哪些模块依赖本模块）
- 可选依赖（什么条件下需要）

## 5. 性能与资源
- 时间复杂度分析
- 内存占用估算
- I/O 模式（读/写频率，数据量级）

## 6. 错误处理
- 异常类型定义
- 降级策略
- 日志级别
```

### Review 检查点（Phase 1 → Phase 2 闸门）

| 检查项 | 通过标准 |
|--------|---------|
| 幻觉排除 | 接口签名全部可编译（类型存在），依赖版本真实存在 |
| 方案对比完整性 | Type-1 决策有 §11.8 的 7 维矩阵；每方案 ≥2 个外部 T1/T2 锚点覆盖 ≥3 维；收敛出口非空 |
| 接口完整性 | 每个公开函数有签名 + 参数说明 + 异常声明 |
| 兼容性 | 不破坏现有 API（或明确标注 breaking change） |
| 性能目标 | 有时间复杂度/内存估算，且合理 |
| 降级策略 | 依赖不可用时有明确 fallback |

## 四、Phase 2: 实施规划 (Implementation)

> 搜索工具与外部案例锚点的硬约束见 §十一。

### 目标
回答"怎么写？分几步？每一步做什么？"——将设计翻译为可执行的任务分解。

### 产出: `docs/IMPL_<topic>.md`

**必须包含的章节：**

```markdown
# [主题] · 实施文档

## 1. 任务分解
- Task 1: [名称] → 文件: xxx, 测试: test_xxx → 预计 N 行
- Task 2: [名称] → 文件: xxx, 测试: test_xxx → 预计 N 行
- ...

## 2. 工程细节
### 2.1 版本约束
- Python >= 3.10
- 依赖包版本（精确到 minor）

### 2.2 文件结构
- 新增文件列表（路径 + 用途）
- 修改文件列表（路径 + 改动范围）

### 2.3 接口签名（完整版）
\`\`\`python
def function_name(
    param1: Type1,  # 描述
    param2: Type2 = default,  # 描述
) -> ReturnType:
    \"\"\"一行摘要。
    
    Args: ...
    Returns: ...
    Raises: ...
    \"\"\"
\`\`\`

### 2.4 性能注意事项
- 避免的低效操作（如 DataFrame.iterrows()、逐行 .loc）
- 推荐的向量化方式
- 缓存策略

### 2.5 测试策略
- 单元测试覆盖范围
- 集成测试覆盖范围
- 边界条件列表
```

### Review 检查点（Phase 2 → Phase 3 闸门）

| 检查项 | 通过标准 |
|--------|---------|
| 幻觉排除 | 所有文件路径存在或计划创建，依赖版本与 pyproject.toml 一致 |
| 任务可行性 | 每个 Task 有明确的文件 + 测试 + 预计行数 |
| 接口签名 | 类型完整，无 `Any` 滥用 |
| 低效操作 | 明确列出禁止的操作模式 |
| 测试覆盖 | 每个 Task 有对应的测试文件 |

## 五、Phase 3: 验收标准 (Checklist)

> 搜索工具与外部案例锚点的硬约束见 §十一。

### 目标
定义"怎么算做完？"——可逐项检查的验收清单。

### 产出: `docs/CHECKLIST_<topic>.md`

**必须包含的章节：**

```markdown
# [主题] · 审查验收清单

## 1. 功能完整性
- [ ] 所有公开 API 已实现
- [ ] 所有配置项已支持
- [ ] 错误处理覆盖所有异常路径

## 2. 测试完整性
- [ ] 单元测试覆盖率 > 80%
- [ ] 集成测试通过
- [ ] 边界条件测试通过
- [ ] 回归测试全部通过（N 个测试）

## 3. 性能验收
- [ ] 时间复杂度符合设计目标
- [ ] 大数据量压测通过（N 条数据 < X 秒）

## 4. 文档一致性
- [ ] 实现与设计文档一致
- [ ] 实现与实施文档一致
- [ ] 接口签名与文档一致
- [ ] 依赖版本与 pyproject.toml 一致

## 5. 兼容性
- [ ] 不破坏现有 API（或 breaking change 已记录在 CHANGELOG）
- [ ] 新增依赖已添加到 pyproject.toml

## 6. 代码质量
- [ ] 无 `# TODO` 残留
- [ ] 无 `print()` 调试代码
- [ ] 日志级别正确
- [ ] 类型标注完整
```

### Review 检查点（Phase 3 → Phase 4 闸门）

| 检查项 | 通过标准 |
|--------|---------|
| 文档一致性 | 调研 → 设计 → 实施 → 清单四份文档之间无矛盾 |
| 前后对齐 | 设计文档中的接口 = 实施文档中的接口 = 清单中的检查项 |
| 版本对齐 | 所有文档引用的依赖版本与 pyproject.toml 一致 |

## 六、Phase 4: TDD 实现

> 搜索工具与外部案例锚点的硬约束见 §十一。

### 目标
严格遵循 TDD 循环：Red → Green → Refactor → 审查验收。

### 流程

```
1. RED:   写失败测试
2. GREEN: 写最小实现让测试通过
3. REFACTOR: 重构代码（测试仍然通过）
4. 回到步骤 1，直到所有测试覆盖
5. 运行全量回归测试
6. 审查验收
```

### 实现约束

| 约束 | 说明 |
|------|------|
| 禁止跳过测试 | 不允许先写实现再补测试 |
| 测试独立性 | 每个测试不依赖其他测试的状态 |
| 回归测试 | 每次实现后运行全量回归 |
| 代码风格 | `black` 格式化，`mypy` 类型检查通过 |

### 审查验收（Phase 4 → Phase 5 闸门）

| 检查项 | 通过标准 |
|--------|---------|
| TDD 完整性 | 所有测试在实现前编写，有 commit 历史可验证 |
| 全量回归 | `pytest tests/` 全部通过 |
| 类型检查 | `mypy` 无新增错误 |
| 代码格式 | `black --check` 通过 |
| 清单验收 | CHECKLIST 中所有项目勾选完成 |

## 九、文档一致性检查矩阵

每份 Spec 文档（调研/设计/实施/清单）在 Review 阶段必须交叉检查：

| 检查对 | 检查内容 |
|--------|---------|
| 调研 ↔ 设计 | 设计方案是否基于调研结论？选择的方案是否在调研中对比过？ |
| 设计 ↔ 实施 | 实施接口是否与设计一致？文件结构是否与设计模块分解一致？ |
| 实施 ↔ 清单 | 清单检查项是否覆盖实施的所有 Task？ |
| 清单 ↔ 设计 | 清单的性能验收标准是否与设计目标一致？ |
| 全部 ↔ pyproject.toml | 依赖版本是否一致？ |

## 十、Trivial 变更豁免

以下变更可跳过 Spec 流程，直接 TDD 实现：

| 变更类型 | 示例 | 最大范围 |
|---------|------|---------|
| Bug 修复 | 修复除零错误 | 单文件，< 50 行 |
| 类型标注补充 | 添加缺失的类型标注 | 不改变运行时行为 |
| 测试补充 | 补充边界条件测试 | 不修改实现代码 |
| 文档修正 | 修正文档中的错误描述 | 不涉及代码 |

**判断标准**：如果变更涉及 > 2 个文件、或新增公开 API、或新增依赖，必须走完整 Spec 流程。

## 十一、设计 / 实施 / 验收 / TDD 阶段的搜索工具调用与外部案例锚点规则

> **增补日期**: 2026-11-04
> **依据**: `F:\Spec_Workflow\SPEC_PROCESS.md` §Step 工具与提示词契约（v1.6）；用户指令（2026-11-04）要求设计、实施、验收、TDD 阶段也建立搜索调用规则并充分寻找外部案例锚点。
> **定位**: 只约束「调用什么通道、留下什么证据」，不新增 RULE 编号、不新增门禁、不新增依赖、不改动 `F:\Spec_Workflow`。
> **与外部规范的关系**: 外部 Step 3/5/7 标注“无（纯文档）”指“无必用外部检索通道”；本节不改变该最小集，只增加「锚点缺失即触发检索」的硬约束。系统性领域调研仍回 Step 1，不在设计文档里堆零散链接。

### 11.1 四条通则

1. **最小集**: 单次触发最多 2 个检索能力（本仓检索 1 个 + 外部检索 1 个）；禁止全量挂载。
2. **只约束形态**: 硬约束必须可核验（有 / 无锚点、ID 可解析 / 不可解析、可重放 / 不可重放），禁止写“充分 / 优质 / 优雅”。
3. **必须配降级链**: `目标通道 → 备用通道 → 已读到的本仓事实 → 「未取证」声明`；工具失败不得静默跳过，须写明走了哪一跳。
4. **环境态隔离**: 规则只写能力类别；具体工具名集中在 §11.6 映射表，工具不可用时按降级链处理。

### 11.2 外部案例锚点分级

| 等级 | 锚点类型 | 可用范围 |
|------|----------|----------|
| T1 一手 | 官方文档 / 标准 / 源码 / 上游测试 / PR / commit | 设计决策、接口实现、验收、测试均可作硬锚点 |
| T2 二手权威 | 维护者 issue / release note / 官方博客 / 维护者答复 | 可作“事实状态”锚点，不替代 T1 的方法学结论 |
| T3 社区 | 技术问答站 / 论坛 / 邮件列表 | 只用于发现反例与工程陷阱，不得作为唯一最佳实践依据 |
| T4 转述 | 聚合博客 / 二手解读 | 只能作线索；数字与结论须回溯 T1/T2，否则标 `[未回原文]` |

**锚点记录格式**（至少满足 3 项，缺一项即不得标“已验证”）：

| 字段 | 要求 |
|------|------|
| 来源类型 | T1 / T2 / T3 / T4 |
| 可解析 ID | URL / arXiv / DOI / commit hash / 上游测试路径 |
| 版本与日期 | 库版本、文档版本或发布日期 |
| 适用性 | 用于哪个决策 / 接口 / 验收项 / 测试场景；与本仓差异 |

### 11.3 分阶段调用规则

| 阶段 | 触发条件（满足即必须检索） | 检索能力（≤2） | 外部锚点最低要求 | 证据出口 |
|------|---------------------------|----------------|------------------|----------|
| Step 3 设计 | 关键决策涉及外部库行为、架构模式、迁移路径、兼容性或性能声明 | 本仓检索 + 通用检索 / 代码检索 | 每个关键决策 ≥1 个 T1/T2 锚点；无锚点只能标 `[无外部锚点-自证]` 并写理由与降级链；被拒绝的替代方案 ≥2 | DESIGN §决策表 + §锚点表 |
| Step 5 实施 | 新增 API / 依赖、签名不直观、迁移步骤或性能敏感路径 | 官方文档检索（含上游源码 / 测试） | 每个新增 API / 依赖 ≥1 个 T1 锚点（官方文档或上游源码 / 测试）；版本必须可查 | IMPL §接口表 + §依赖表 |
| Step 7 验收 | 验收项断言外部行为、数值阈值或兼容性 | 官方文档 / 上游测试 / issue 检索 | 每条行为验收项 ≥1 个 T1/T2 锚点，或本地 E1 测试；禁止无证据的 ✅ | CHECKLIST §锚点列 + DoR/DoD |
| Step 9 TDD | 测试行为由外部规范、上游实现或已知缺陷定义 | 上游测试 / issue repro / 标准条款检索 | 每个测试文件 ≥1 个 T1/T2 锚点（上游测试 / 标准条款 / 可复现 issue）；无外部场景只能标 `[合成场景]` 并写理由；正例 + 边界反例各 ≥1 | §fixture 表 + 红→绿记录 |

### 11.4 硬约束

1. **无锚点不得写 ✅**：只能标 `[未验证]`、`[无外部锚点-自证]` 或 `[未取证]`，并写降级链。
2. **设计阶段**: 外部案例只证明“别人这样做”，不能替代“本仓适用性”论证；须在 DESIGN 中写明差异与代价。
3. **实施阶段**: 依赖版本、API 签名、迁移命令必须来自 T1 锚点或本仓可执行验证；禁止凭记忆写版本号或函数名。
4. **验收阶段**: 每条验收项必须有锚点或本地 E1 证据；统计类汇总只能来自逐项核对表。
5. **TDD 阶段**: 先写会失败的测试，再写实现；测试必须包含正例与反例（边界 / 异常输入）；只写“请用 TDD”不算。
6. **引用核验**: 锚点 ID 必须可解析；不可解析只能标“未验证”，禁止标“已验证”；LLM 不得自任引用验证器。
7. **不懂不要乱写**: 未理解或未验证的规则、案例、版本、API、测试场景不得写入；必须先检索或阅读原件，无法理解则标 `[未理解-待核]` 并停止扩写。

### 11.5 反模式（须显式避免）

- 搜到了就当作 T1（把 T4 当一手来源）。
- 单源写成共识（必须写“单源”并标 `[单源-待二核]`）。
- 工具失败静默跳过（必须写降级链走了哪一跳）。
- 无锚点却打 ✅；或先写结论再补链接。
- 编造 issue / commit / 版本 / API / 测试用例。
- 不懂装懂：用未读过的文档、未验证的案例或猜想的版本/API 充填锚点。
- 用“外部有案例”替代本仓证据与适用性分析。
- 为凑锚点堆砌无关链接（锚点必须与当前决策 / 接口 / 验收 / 测试直接对应）。

### 11.8 方案对比矩阵（7 维 × 外部锚点）

> **依据**: `F:\Spec_Workflow\spec\templates\DECISION_MATRIX_TEMPLATE.md` v1.0 @ `bf83e48`（维度逐行固定为七维）；用户指令（2026-11-04）要求对成本 / 收益 / 兼容 / 维护 / 升级潜力 / 短期 / 长期逐维调研，并附外部证据锚点。

#### 11.8.1 启用判据

| 判据 | 要求 |
|------|------|
| 可逆性 | Type-1：无回退点 / 变更真值源或契约 |
| 方案数 | ≥2 个真实候选；写不出候选 = 调研不足，回 Step 1 |

#### 11.8.2 七维定义与最低证据

| 维度 | 含义 | 最低证据 |
|------|------|----------|
| 成本 | 开发 / 迁移 / 运行成本 | E1 本仓 diff / 任务量，或 T1 外部基准；禁止只写“低 / 高” |
| 收益 | 功能 / 性能 / 风险降低 | T1/T2 外部案例 + 本仓适用性 |
| 兼容 | API / 数据 / 依赖 / 版本 | T1 官方文档，或 E1 本仓兼容测试 |
| 维护（可维护性） | 复杂度 / 测试面 / 文档面 | E1 代码面统计，或 T1 上游维护记录 |
| 升级潜力 | 扩展点 / 替换成本 / 生态寿命 | T1/T2 上游路线图 / 版本历史 |
| 短期 | 本次迭代可落地性（时间窗由矩阵声明，见 11.8.3） | E1 任务量 / 依赖可用性 |
| 长期 | 演进与退出成本（时间窗由矩阵声明，见 11.8.3） | T1/T2 生态 / 维护周期；无法核实标 `[待核]` |

#### 11.8.3 矩阵前置声明、每格格式与锚点要求

**矩阵前置声明（必填；缺任一项则矩阵不成立）**：

- **时间口径**: 「短期」与「长期」必须以可机械识别的时间窗或迭代边界定义（如「短期 = 本次迭代内 / 本批 Spec 周期」「长期 = ≥N 个季度 / 项目生命周期」）；同一矩阵内口径固定，不得逐格改动
- **Type-1/Type-2 判定**: 须逐项勾选并写判定依据（回退点是否存在）；判为 Type-2 则不启用矩阵
- **证据等级取值域**: E1~E5 或 `待核`，不得另造等级

**逐格要求**：

- **格格式**: `评估（E?；YYYY-MM-DD；锚点 ID/URL 或 [本仓证据]）`
- **计数 / 占比**: 必须附复算命令（声明 = 机械重数）；无法复算的数字不得写入格内，只能改定性评估
- **外部锚点最低要求**: 每个方案 ≥2 个外部 T1/T2 锚点，覆盖 ≥3 个维度；其余格可为 E1/E2 本仓证据
- **逐行覆盖**: 每个维度行至少 1 个方案给出外部锚点；否则整行标 `[无外部锚点-自证]` 并写理由与降级链
- **适用性**: 锚点须写明外部环境与本仓差异，禁止直接照搬外部结论
- **未验证**: 无外部锚点的格不得标“已验证”；未知标 `[待核]` 或 `[未理解-待核]`

#### 11.8.4 收敛出口（必填）

- 选定方案 + 一句话理由
- 被拒方案 + 拒绝理由 + 代价
- 未闭合项四元块（判据 / 触发条件 / 当前倾向 / 证据等级）；无则写「（无）」
- 不得以“还需更多维度 / 再调研”收尾；确需再调研须给出可机械识别的触发条件

#### 11.8.5 反模式（须显式避免）

- 分析瘫痪：维度无限扩张，每轮只新增未决项而不关闭
- criteria gaming：格子填满但结论未推进；指标被优化而非被满足
- 随机选择：无矩阵或矩阵无收敛出口
- 用无关锚点凑数；把 E4/E5 判断陈述当硬证据
- 只写优点不写缺点；成本只写“低 / 高”而无依据
- 用“外部有案例”替代本仓适用性论证
