# Spec 驱动开发规范

> 版本: v1.0.0 | 生效日期: 2026-06-20 | 适用范围: Factor_Trading_v3.0 全项目

---

## 零、核心原则

1. **所有非 trivial 变更必须先有 Spec 文档，再有代码。**
2. **Spec 文档之间必须交叉验证一致性，消除幻觉和矛盾。**
3. **TDD 是代码实现的唯一入口——先写测试，再写实现。**
4. **每个阶段结束时必须 Review 通过才能进入下一阶段。**

---

## 一、Spec 开发流程总览

```
Phase 0: 调研 ──────────► 调研文档 (RESEARCH_xxx.md)
         │                     │
         │  Review: 排除幻觉    │
         ▼                     ▼
Phase 1: 设计 ──────────► 设计文档 (DESIGN_xxx.md)
         │                     │
         │  Review: 排除幻觉    │
         ▼                     ▼
Phase 2: 实施规划 ───────► 实施文档 (IMPL_xxx.md)
         │                     │
         │  Review: 排除幻觉    │
         ▼                     ▼
Phase 3: 验收标准 ───────► 审查清单 (CHECKLIST_xxx.md)
         │                     │
         │  Review: 文档一致性  │
         ▼                     ▼
Phase 4: TDD 实现 ───────► 测试 + 代码
         │                     │
         │  Review: 审查验收    │
         ▼                     ▼
Phase 5: 完成 ───────────► 归档 + 更新 DEVLOG.md
```

---

## 二、Phase 0: 调研 (Research)

### 目标
回答"我们要做什么？别人怎么做的？有什么坑？"——不涉及任何实现细节。

### 工具
- MCP 学术搜索: `search_papers`, `search_arxiv`, `search_semantic` 等
- MCP 网页搜索: `search_web`, `search_news`
- WebFetch: 获取论文全文、技术博客
- 本地代码库搜索: `SearchCodebase`, `Grep`

### 产出: `docs/RESEARCH_<topic>.md`

**必须包含的章节：**

```markdown
# [主题] · 调研文档

## 1. 问题定义
- 核心问题是什么？
- 为什么现在需要解决？
- 影响范围（哪些模块？）

## 2. 文献调研
- 学术论文（标题 + 链接 + 关键发现）
- 开源实现（仓库 + 成熟度评估）
- 工业界实践（框架/公司 + 做法）

## 3. 方案对比
- 方案 A: 描述 + 优点 + 缺点
- 方案 B: 描述 + 优点 + 缺点
- 方案 C: 描述 + 优点 + 缺点
- 选型决策 + 理由

## 4. 风险识别
- 已知风险 + 缓解策略
- 未知风险 + 如何探测

## 5. 调研结论
- 推荐方案
- 关键假设
- 下一步
```

### Review 检查点（Phase 0 → Phase 1 闸门）

| 检查项 | 通过标准 |
|--------|---------|
| 幻觉排除 | 所有论文/项目可验证（有链接/DOI），不存在虚构引用 |
| 方案完整性 | 至少对比 2 个方案，选型有明确理由 |
| 风险覆盖 | 至少列出 3 个已知风险 + 缓解策略 |
| 假设明确 | 关键假设被显式声明，后续可验证 |

## 三、Phase 1: 设计 (Design)

### 目标
回答"怎么做？架构是什么？接口长什么样？"——基于调研文档，产出可审查的设计。

### 产出: `docs/DESIGN_<topic>.md`

**必须包含的章节：**

```markdown
# [主题] · 设计文档

## 1. 设计目标
- 基于调研文档的选型决策
- 量化的设计目标（如"延迟 < 10ms"、"代码行数 < 500"）

## 2. 架构设计
- 模块分解图（ASCII art）
- 数据流图
- 模块职责边界

## 3. 接口定义
- 公开 API 签名（函数名 + 参数类型 + 返回类型 + 异常）
- 配置项定义（字段名 + 类型 + 默认值 + 约束）
- 向后兼容性说明

## 4. 依赖分析
- 运行时依赖（包名 + 版本约束 + 用途）
- 内部依赖（哪些模块依赖本模块）
- 可选依赖（什么条件下需要）

## 5. 性能与资源
- 时间复杂度分析
- 内存占用估算
- I/O 模式（读/写频率，数据量级）

## 6. 错误处理
- 异常类型定义
- 降级策略
- 日志级别
```

### Review 检查点（Phase 1 → Phase 2 闸门）

| 检查项 | 通过标准 |
|--------|---------|
| 幻觉排除 | 接口签名全部可编译（类型存在），依赖版本真实存在 |
| 接口完整性 | 每个公开函数有签名 + 参数说明 + 异常声明 |
| 兼容性 | 不破坏现有 API（或明确标注 breaking change） |
| 性能目标 | 有时间复杂度/内存估算，且合理 |
| 降级策略 | 依赖不可用时有明确 fallback |

---

## 四、Phase 2: 实施规划 (Implementation)

### 目标
回答"怎么写？分几步？每一步做什么？"——将设计翻译为可执行的任务分解。

### 产出: `docs/IMPL_<topic>.md`

**必须包含的章节：**

```markdown
# [主题] · 实施文档

## 1. 任务分解
- Task 1: [名称] → 文件: xxx, 测试: test_xxx → 预计 N 行
- Task 2: [名称] → 文件: xxx, 测试: test_xxx → 预计 N 行
- ...

## 2. 工程细节
### 2.1 版本约束
- Python >= 3.10
- 依赖包版本（精确到 minor）

### 2.2 文件结构
- 新增文件列表（路径 + 用途）
- 修改文件列表（路径 + 改动范围）

### 2.3 接口签名（完整版）
\`\`\`python
def function_name(
    param1: Type1,  # 描述
    param2: Type2 = default,  # 描述
) -> ReturnType:
    \"\"\"一行摘要。
    
    Args: ...
    Returns: ...
    Raises: ...
    \"\"\"
\`\`\`

### 2.4 性能注意事项
- 避免的低效操作（如 DataFrame.iterrows()、逐行 .loc）
- 推荐的向量化方式
- 缓存策略

### 2.5 测试策略
- 单元测试覆盖范围
- 集成测试覆盖范围
- 边界条件列表
```

### Review 检查点（Phase 2 → Phase 3 闸门）

| 检查项 | 通过标准 |
|--------|---------|
| 幻觉排除 | 所有文件路径存在或计划创建，依赖版本与 pyproject.toml 一致 |
| 任务可行性 | 每个 Task 有明确的文件 + 测试 + 预计行数 |
| 接口签名 | 类型完整，无 `Any` 滥用 |
| 低效操作 | 明确列出禁止的操作模式 |
| 测试覆盖 | 每个 Task 有对应的测试文件 |

---

## 五、Phase 3: 验收标准 (Checklist)

### 目标
定义"怎么算做完？"——可逐项检查的验收清单。

### 产出: `docs/CHECKLIST_<topic>.md`

**必须包含的章节：**

```markdown
# [主题] · 审查验收清单

## 1. 功能完整性
- [ ] 所有公开 API 已实现
- [ ] 所有配置项已支持
- [ ] 错误处理覆盖所有异常路径

## 2. 测试完整性
- [ ] 单元测试覆盖率 > 80%
- [ ] 集成测试通过
- [ ] 边界条件测试通过
- [ ] 回归测试全部通过（N 个测试）

## 3. 性能验收
- [ ] 时间复杂度符合设计目标
- [ ] 大数据量压测通过（N 条数据 < X 秒）

## 4. 文档一致性
- [ ] 实现与设计文档一致
- [ ] 实现与实施文档一致
- [ ] 接口签名与文档一致
- [ ] 依赖版本与 pyproject.toml 一致

## 5. 兼容性
- [ ] 不破坏现有 API（或 breaking change 已记录在 CHANGELOG）
- [ ] 新增依赖已添加到 pyproject.toml

## 6. 代码质量
- [ ] 无 `# TODO` 残留
- [ ] 无 `print()` 调试代码
- [ ] 日志级别正确
- [ ] 类型标注完整
```

### Review 检查点（Phase 3 → Phase 4 闸门）

| 检查项 | 通过标准 |
|--------|---------|
| 文档一致性 | 调研 → 设计 → 实施 → 清单四份文档之间无矛盾 |
| 前后对齐 | 设计文档中的接口 = 实施文档中的接口 = 清单中的检查项 |
| 版本对齐 | 所有文档引用的依赖版本与 pyproject.toml 一致 |

## 六、Phase 4: TDD 实现

### 目标
严格遵循 TDD 循环：Red → Green → Refactor → 审查验收。

### 流程

```
1. RED:   写失败测试
2. GREEN: 写最小实现让测试通过
3. REFACTOR: 重构代码（测试仍然通过）
4. 回到步骤 1，直到所有测试覆盖
5. 运行全量回归测试
6. 审查验收
```

### 实现约束

| 约束 | 说明 |
|------|------|
| 禁止跳过测试 | 不允许先写实现再补测试 |
| 测试独立性 | 每个测试不依赖其他测试的状态 |
| 回归测试 | 每次实现后运行全量回归 |
| 代码风格 | `black` 格式化，`mypy` 类型检查通过 |

### 审查验收（Phase 4 → Phase 5 闸门）

| 检查项 | 通过标准 |
|--------|---------|
| TDD 完整性 | 所有测试在实现前编写，有 commit 历史可验证 |
| 全量回归 | `pytest tests/` 全部通过 |
| 类型检查 | `mypy` 无新增错误 |
| 代码格式 | `black --check` 通过 |
| 清单验收 | CHECKLIST 中所有项目勾选完成 |

---

## 七、Phase 5: 归档

### 产出

1. 更新 `CHANGELOG.md`
2. 更新 `DEVLOG.md`（开发日志）
3. 更新 `DECISIONS.md`（如有关键决策）
4. 将 Spec 文档标记为 `状态: 已完成`
5. Git commit 引用所有相关文档

## 八、文档命名规范

| 文档类型 | 命名格式 | 示例 |
|---------|---------|------|
| 调研文档 | `RESEARCH_<topic>.md` | `RESEARCH_vectorized_backtest.md` |
| 设计文档 | `DESIGN_<topic>.md` | `DESIGN_vectorized_backtest.md` |
| 实施文档 | `IMPL_<topic>.md` | `IMPL_vectorized_backtest.md` |
| 验收清单 | `CHECKLIST_<topic>.md` | `CHECKLIST_vectorized_backtest.md` |

| 开发日志 | `DEVLOG.md` | — |
| 架构文档 | `ARCHITECTURE.md` | — |
| 决策记录 | `DECISIONS.md` | — |

## 九、文档一致性检查矩阵

每份 Spec 文档（调研/设计/实施/清单）在 Review 阶段必须交叉检查：

| 检查对 | 检查内容 |
|--------|---------|
| 调研 ↔ 设计 | 设计方案是否基于调研结论？选择的方案是否在调研中对比过？ |
| 设计 ↔ 实施 | 实施接口是否与设计一致？文件结构是否与设计模块分解一致？ |
| 实施 ↔ 清单 | 清单检查项是否覆盖实施的所有 Task？ |
| 清单 ↔ 设计 | 清单的性能验收标准是否与设计目标一致？ |
| 全部 ↔ pyproject.toml | 依赖版本是否一致？ |

---

## 十、Trivial 变更豁免

以下变更可跳过 Spec 流程，直接 TDD 实现：

| 变更类型 | 示例 | 最大范围 |
|---------|------|---------|
| Bug 修复 | 修复除零错误 | 单文件，< 50 行 |
| 类型标注补充 | 添加缺失的类型标注 | 不改变运行时行为 |
| 测试补充 | 补充边界条件测试 | 不修改实现代码 |
| 文档修正 | 修正文档中的错误描述 | 不涉及代码 |

**判断标准**：如果变更涉及 > 2 个文件、或新增公开 API、或新增依赖，必须走完整 Spec 流程。
