## 三、已确认功能冲突分析

### 3.1 冲突1: Pending Order Queue × Universe Filter 时序问题

**场景**: ① 信号生成日，股票 A 正常可交易，创建 pending order → ② 次日，股票 A 停牌 → ③ pending order 仍尝试执行

**代码路径**:
- 信号生成时: [engine.py#L521-L532](file:///f:/Coding/Factor_Trading_v3.0/core/engine.py#L521-L532) 创建订单加入队列
- 订单执行时: [engine.py#L259-L331](file:///f:/Coding/Factor_Trading_v3.0/core/engine.py#L259-L331) `_process_pending_orders()` 直接执行
- **问题**: `_process_pending_orders()` 中**未调用 `universe.filter_stocks()`** 再次校验

**风险等级**: 🟡 中 — 停牌后仍尝试买入，但 `execute_order()` 中的价格校验 (10% 偏差) 会触发 warning，实际执行可能失败

**修复建议**:
```python
def _process_pending_orders(self, date, date_index):
    for order in pending_orders:
        # 新增: 再次校验可交易性
        if self.universe and not self.universe.tradable.loc[date, order.stock]:
            self.pending_queue.cancel_orders(order.stock, date)
            logger.warning(f"取消{order.stock}订单: 当日不可交易")
            continue
        # ... 原有执行逻辑
```

### 3.2 冲突2: Guard Pipeline × Pending Order 重复检查

**场景**: 引擎在信号生成阶段调用 Guard Pipeline 检查，但 pending order 执行时不再经过 Guard

**代码路径**:
- Guard 检查: V2 引擎的插件系统 (engine_plugins.py)
- Pending 执行: [engine.py#L304](file:///f:/Coding/Factor_Trading_v3.0/core/engine.py#L304) 直接 `executor.execute_pending_order()`

**风险等级**: 🟡 中 — 信号生成时通过 Guard 的订单，延迟执行时账户状态可能已变化 (如回撤扩大)

**修复建议**: 在 `_process_pending_orders()` 中增加 Guard 二次检查

### 3.3 冲突3: V3 Vector Engine 未集成 Pending Order + Universe Filter

**现状**: V3 引擎 (`engine_v3_vector.py`) 完全没有使用 `PendingOrderQueue` 和 `UniverseFilter`

**代码对比**:
- V1/V2: 完整的 `self.pending_queue` + `self.universe` 集成
- V3: 零引用

**风险等级**: 🔴 高 — V3 作为性能主引擎，缺失订单管理和过滤，导致结果不可比

**修复建议**: 将 PendingOrderQueue 和 UniverseFilter 集成到 V3，使用向量化方式批量处理

### 3.4 冲突4: EventLog 双写 vs PendingOrder 事件日志 重复

**场景**: 系统有两套事件日志:
- `EventLog` (event_log.py): JSONL 持久化 + Ring Buffer
- `PendingOrderQueue._event_log`: 内存 List，仅通过 `get_event_log()` 导出

**风险等级**: 🟢 低 — 两套日志不冲突，但维护成本高，数据可能不一致

**修复建议**: 统一使用 EventLog 作为唯一事件存储
