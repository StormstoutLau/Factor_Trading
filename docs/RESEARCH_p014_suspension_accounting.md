## 4. 复现证据（E2，场景自选理由）

### 4.1 场景

沿用 P-013 G3 的价格序列（含一次真实涨停）并叠加 `suspend[12:14, 1] = 1`（600000 于 2024-01-18 / 01-19 停牌）；20 个交易日 × 3 只股票、真实费用、`n_codes=3`、日频再平衡。**选择理由**：这正是 P-013 最初触发缺陷的夹具形态（含掩码 + 停牌 + 费用），且同时覆盖两条执行路径（仅切换 `enable_pending_orders`）。

### 4.2 读数（E1，可重放：同一脚本切换布尔量）

| 读数 | `enable_pending_orders=False`（次日路径） | `enable_pending_orders=True`（队列路径） |
|------|------------------------------------------|----------------------------------------|
| 600000 停牌期持仓（01-18 / 01-19 收盘） | 338600 / 338600（未变） | 338600 / 338600 |
| 01-22 恢复日 600000 成交 | `SELL 113600` + `SELL 338600` + `SELL 338600`（**三笔**） | `SELL 338600`（**一笔**） |
| 01-22 收盘持仓 | **-113600**（负持仓） | 0 |
| I2 违规 | **5 项**（01-22 至 01-26） | **0 项** |
| 01-22 开盘前队列 | 7 单，其中 600000 卖单 3 笔（113600 / 338600 / 338600） | 1 笔（338600） |

### 4.3 症状校准（**修正原登记**）

| 原 F-S9-G1 描述 | 本次复现 | 处置 |
|-----------------|----------|------|
| 停牌日仍发生买入 | **未复现**：停牌日 600000 的买卖均被掩码拦截（P9 读码 + 实测 0 笔） | 原描述可能来自当时价格污染（F-S9-G2）下的日期/数量误读；本批以复现结果为准，PROGRESS 同步订正 |
| 恢复日同一卖出重复记账 | **已复现**（`SELL 338600` ×2） | 本批修复目标 |
| 负持仓 -109500 + 5 项 I2 违规 | 负持仓 **-113600** + 5 项 I2（数量随价格构造变化） | 本批修复目标 |

### 4.4 机制链（E1 队列快照 + E3 读码）

1. 01-17 收盘持仓 600000 = 338600；再平衡生成 `SELL 113600`（次日执行）。
2. 01-18 停牌 → 掩码拦截，订单留在 `_next_day_orders`（P3 无取消、P4 无过期）。
3. 01-18 再平衡：600000 被 `tradable_mask` 排除 → 目标 0 → 以**当前持仓 338600** 生成 `SELL 338600`（P7/P8：不扣在途 113600）。
4. 01-19 同上 → 再生成一笔 `SELL 338600`。
5. 01-22 恢复 → 三笔卖单依次成交（P5 无持仓夹紧）→ 338600 − 113600 − 338600 − 338600 = **-452200**；当日随后又被陈旧买单拉回 -113600。
6. 队列路径因 P2 的「再平衡先全量撤单」恰好只保留最后一笔，故不产生重复。

### 4.5 关联观察（非 P1，但同源）

| 观察 | 证据 |
|------|------|
| 陈旧买单无过期：01-17 生成的 `000001 BUY 305500`（现金不足失败）被重试到 01-29（12 个自然日），全程未成交 | 队列快照 01-23~01-29 均含 create=2024-01-17 |
| 停牌持仓被强制转为「清仓目标」（语义争议）：停牌只是暂时不可交易，是否应被优化器排除并强制清仓，属策略语义问题 | P7；本批**不改**，登记为 U-P014-1 |

## 5. 影响面

| 面 | 结论 |
|----|------|
| 生产默认路径（队列） | 账目正确；但同样缺「持仓夹紧」防线（仅靠撤单规避） |

| 退市结算 / 末日强平 | 卖出量取 `position.quantity`，天然不超过持仓（P12），无风险 |

## 6. 约束

1. 不得改变「停牌不可交易」掩码语义（P9 正确）；
2. 不得引入 `core/` 以外的新依赖；
3. 两条执行路径必须共享同一套账目防线，禁止只修一条；
4. 修复后 golden 基线若变化，必须按 A20/D10 说明 diff 合理性后重录；
5. 生产代码改动仅限 `core/engine_v2.py`（不改 `tracker.py` 的持仓语义，避免影响期货/融券空头）。

## 7. 方案矩阵（Step 3 输入）

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| **U-A 执行侧夹紧**（只做） | 卖出前 `min(订单量, 可卖持仓)`；无持仓则作废订单 | 最小改动；任何路径都不会负持仓 | 治标：重复订单仍生成、仍占队列，且买侧陈旧订单仍在 | **采纳（作为防线）** |
| **U-B 生成侧在途感知** | 目标持仓扣除在途订单净额 | 从源头消除重复 | 需改 `build_target_positions` 契约与两条生成路径；`total_value`/现金语义需重定义；回归面最大 | 不采纳（本批） |
| **U-C 路径语义对齐** | 次日路径复用队列路径的「再平衡先撤单」 | 一条语义规则；消除重复与陈旧单；改动集中在 `_execute_rebalance` | 会改变 G3 等已有基线的成交明细（需重录） | **采纳** |
| **U-D 订单过期** | 次日路径复用 `PendingOrder.is_expired` | 与队列路径同语义；防止无再平衡时订单永久滞留 | 单独使用不解决重复 | **采纳** |
| **U-E 持仓层禁止负值** | 在 `Position.execute_trade` 截断卖出 | 一处覆盖所有路径 | 会影响期货/融券空头语义；静默篡改成交量，账实不符 | 不采纳（越界） |

**组合决策**：U-A + U-C + U-D（三层：语义对齐 → 过期 → 执行兜底）。

## 9. 结论

缺陷可稳定复现，根因是**次日开盘路径缺少「再平衡刷新订单簿」与「订单过期」两条既有语义**，叠加**执行侧无持仓夹紧**。修复面收敛在 `core/engine_v2.py` 的三个函数，不需要触碰持仓模型与掩码层。
